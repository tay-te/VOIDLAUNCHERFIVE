# VOID Atlas — performance

Atlas must never be the reason a frame is late. The budgets, and how they are held:

| Budget | Why it holds |
|---|---|
| Minimap ≤ 0.3 ms per frame | One mesh per atlas page (tiles clipped to the rounded square on the CPU, a few dozen vertices each), markers culled to the square, text from pre-rasterised Outfit sizes. |
| Map screen avg frame ≤ 4 ms (≥ 250 fps), p99 ≤ 8 ms while panning and zooming | The world behind the map is drawn once and kept as a still (`Backdrop`), so the frame only draws the map; tiles live in four 2048² atlas pages (one draw per page); mip levels keep the visible tile count near a dozen at any zoom. |
| Chunk ingest ≤ 1 ms of client-thread time in any frame | The client thread only queues chunks (400 µs budget per frame); reading columns, drawing regions, assembling and dithering tiles all happen on worker threads; uploads are time-boxed (1.2 ms) and patch only the changed rectangle of a tile. |
| No hitch > 33 ms | No disk I/O, no texture reads, no allocation of big buffers on the client thread; the block colour table is built once per world join (and resource reload); the GPU pages are made while the world loads; a layer lists its region files on a worker. |
| Underground map avg frame ≤ 4 ms, p99 ≤ 8 ms | Slices are layers like the surface: the same atlas pages, mip levels and time-boxed uploads. |
| Structure detection ≤ 0.5 ms per chunk (worker) | Palette counts per section; only sections with an anchor (a bell, a spawner...) are walked, a handful of anchors per chunk judged. |
| Underground reveal ≤ 20 ms per walk (worker) | A breadth-first walk of at most 60,000 open blocks in a 24-block sphere, run when the player has moved 3 blocks, one at a time. |

## How it is measured

`./gradlew atlasPerf -Pbackend=opengl` (or `vulkan`) runs the `perf` mode of the client game test
(`src/gametest/.../AtlasGameTest.java`) uncapped — vsync off, no frame limit, no background throttling — at
1920 × 1080:

1. **Flight**: the player flies (spectator, sprinting) over freshly generated land for 12 s with the minimap on;
   chunks stream in and Atlas reads them. Recorded per frame: frame time, minimap cost (`MinimapHud.extract`, CPU),
   client-thread ingest time.
2. **Cave**: the player is taken through a real cave near spawn, stop by stop; the underground reveal is timed on the
   workers. Structure detection is timed during the flight.
3. **Map**: 256 regions (16 × 16, 8192 × 8192 blocks) of synthetic land are drawn into the map, then the full map
   is opened and a script pans across it while zooming from 4 px/block out to 1/32 px/block and back, twice, for
   12 s — every mip level and a few hundred tiles pass through the view. Recorded per frame: frame time, Atlas's map
   CPU time, tiles drawn; and the tile uploads.
4. **Underground map**: 256 regions of a synthetic cave slice, panned and zoomed the same way on the Underground
   view.

The run writes `build/perf/<backend>.json`, rewrites the table below, and **fails the build** if any budget is
exceeded (`atlasPerf` in `build.gradle` holds the budgets).

## Hitches that are not Atlas's

Every frame over 25 ms is logged with where its time went (ingest, minimap, map page, uploads, tick, HUD, GC) and the
JVM's uptime, and the perf run logs every pause of the whole JVM to `build/run/atlasPerf/safepoints.log`. A long frame
in which Atlas's own phases are small is the game's, the driver's, or the machine's.

`./gradlew atlasPerf -Pbackend=<b> -Patlas.baseline=true` flies the same route with Atlas loaded but idle (no session,
no chunk reading, no HUD) and writes `build/perf-baseline/<b>.json`. On 2026-10-05, with other sessions' clients and a
benchmark running on the same machine, the idle baseline's worst flight frame was 20.5 ms on Vulkan and **118.9 ms on
OpenGL**; the Vulkan flight hitches of 45–51 ms seen earlier that day had Atlas at 0.3 ms of the frame, no uploads and
no GC. The longest JVM pauses in a logged run were G1 young collections of 20–29 ms, which is also what the minimap's
worst frame is: it lands in a different phase (setup, tiles, "rest") from run to run.

One hitch was Atlas's and is fixed: the map rebuilt the place snapshot under the place book's lock on the render
thread, so it waited (185 ms) behind a worker naming the areas of a few hundred regions. The writers now publish the
snapshot as they finish, the render thread only reads it, and the proximity check runs on a worker.

**2026-10-06, after the waypoints / minimap / reliability upgrade** (beams for 48 waypoints, the radar, the shape pins
and the world finder all on in the flight). Under other sessions' load (three Hearth game tests, 50–70% CPU), the
Atlas-idle baseline's worst flight frame was 32.2 ms on Vulkan and 22.7 ms on OpenGL, run back to back with the table
above. Vulkan's one over-budget frame (35.2 ms) had Atlas at 0.6 ms of it (minimap 0.46, beams 0.17) and a GC; the
OpenGL map-screen p99 of 21.8 ms came with Atlas's own map CPU at its usual 1.4 ms a frame. On a quiet machine the
same build measured: minimap 0.24 / 0.29 ms, beams 0.11–0.12 ms, radar 0.03 ms (OpenGL / Vulkan).
